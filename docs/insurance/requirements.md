# 医疗险保障比较 · 业务任务书

[课程指南](course-guide.md) · [资料与设计参考](references.md) · [手册目录](../../README.md)

本项目面向中国内地准备了解医疗险的投保用户。核心任务是把用户的关注点变成一份能够逐项查看依据的保障比较报告，帮助用户发现仍需了解的条件。

这份任务书规定当前本地咨询工作区的输入、处理规则、交付内容和验收标准。业务围绕投保前的需求理解与保障比较展开，状态与接口细节见 [执行设计](architecture.md)。

## 1. 用户要完成什么

一个典型问题是：“我在看两份医疗险，更在意普通门诊能否保障、以后怎样续保，请帮我比较。”

这句话还没有给出具体产品与版本，也没有说明“普通门诊”和“续保”各自有哪些条款条件。系统需要先把对象与关注点确定下来，再读取资料，最终给出有出处的对照。年龄、医保情况和预算可以补充，但缺少报价时，预算数字本身不能产生价格结论。

| 用户的动作 | 系统应完成的业务任务 | 用户得到什么 |
| --- | --- | --- |
| 描述关注点，选择产品 | 整理待确认提案，检查关注维度和比较对象 | 需求草稿、明确的补充问题及可编辑字段 |
| 确认 2–3 个产品及资料版本 | 将比较绑定到具体目录记录 | 本次比较范围及资料性质 |
| 确认需求并开始查证 | 创建后台运行，按选定版本取证，整理字段 | 执行进度、停止入口、保障对照与来源 |
| 查看差异和缺口 | 区分有依据的事实、未提供信息和待核实条件 | 比较关注点、资料缺口和下一步 |
| 追问当前报告 | 筛选该报告已保存的相关证据 | 带出处与适用条件的回复，或资料不足说明 |
| 补充需求或改变选择 | 用更新后的请求重新比较，保存前次结果 | 可以回看的多轮记录 |

系统的交付不是一句“哪款最好”，而是说明：两份资料分别写了什么，哪些内容与用户关注点有关，还有哪些问题不能由当前资料回答。

## 2. 输入契约

网页确认后的需求和命令行需求文件使用同一组业务字段：

```json
{
  "question": "比较这两份医疗险资料。我关心普通门诊和续保安排，年度预算2000元；哪些差异有依据，哪些还需要确认？",
  "profile": {
    "focus": ["coverage", "renewal"],
    "annual_budget": 2000,
    "age": 30,
    "social_insurance": "yes"
  },
  "selections": [
    {"product_id": "demo_hospital", "version": "demo-v1"},
    {"product_id": "demo_outpatient", "version": "demo-v1"}
  ]
}
```

这是课程主案例的请求。年龄与预算也可以用 `null` 表示未提供，医保情况用 `unknown` 表示未知。

| 字段 | 作用与要求 |
| --- | --- |
| `question` | 用户本次想了解的问题，与结构化关注点共同构成任务 |
| `profile.focus` | 必须明确至少一个关注维度；不能根据“随便看看”替用户猜出优先级 |
| `profile.annual_budget` | 可选的年度预算，以人民币计；没有适用报价时仍保持预算匹配未知 |
| `profile.age` | 可选年龄；不由年龄单独推出可投保或保费 |
| `profile.social_insurance` | `yes`、`no` 或 `unknown`；不得代替具体产品的适用条件检查 |
| `selections` | 选择 2–3 个产品，每项同时提供 `product_id` 和 `version` |

关注点只使用下面九个维度。用户可以重点看其中几项，比较报告仍应让其查看其他维度的资料状态。

| 维度 | 字段值 | 应回答的问题 |
| --- | --- | --- |
| 保障责任 | `coverage` | 资料列出了哪些保障内容及其条件？ |
| 免赔额 | `deductible` | 怎样扣除免赔额，有哪些适用条件？ |
| 赔付比例 | `reimbursement` | 条款给出的比例与前提是什么？ |
| 医院范围 | `hospital` | 哪些医疗机构或就医范围被资料列明？ |
| 等待期 | `waiting_period` | 资料怎样规定等待期及例外？ |
| 续保 | `renewal` | 续保条件和相关限制怎样表述？ |
| 免责 | `exclusions` | 资料列明了哪些不承担责任的情形？ |
| 保费 | `premium` | 是否有适用于本次条件的报价？ |
| 健康告知 | `underwriting` | 资料是否说明告知、核保或其他待确认要求？ |

这些问题是提取与比较的方向，不表示每份资料都包含答案。短摘录没有提到某项时，应写明未提供，不能据此推断产品没有该项限制或责任。

### 何时需要补充询问

- 关注点缺失时，先请用户选择想比较的维度。
- 产品不足时，先请用户补充比较对象；重复产品或无法识别的版本属于输入错误，需要纠正选择。
- 年龄、医保或预算尚未提供时，可以比较已有条款；涉及这些条件的判断保持待确认。
- 用户修改需求后，以新请求为本次依据，历史结果保留供对照。

补充询问应指出缺少什么、为什么影响当前比较。已有的有效信息不应被无故清空。

聊天提案只允许修改年龄、年度预算、医保情况和关注维度，模型提取的字段必须附本轮用户原话。提案与已确认需求分开保存；用户在需求卡中核对后才应用。产品和版本只由用户选择，不根据自然语言描述自动补入。资料模式采用明确关键词与数值规则，复杂表达可以直接在需求卡中修正。

## 3. 产品资料与版本契约

目录采用两类资料：

| 资料组 | 范围 | 使用方式 |
| --- | --- | --- |
| 自拟教学产品 | `demo_hospital`、`demo_outpatient`、`demo_renewal`，版本 `demo-v1` | 提供九维资料结构，包括明确的保费未知项，用于练习比较与边界检查 |
| 官方条款摘录 | 三份官方公开资料的少量片段 | 展示实际条款的引用方式与资料缺口，不推断完整合同内容 |

一次比较使用同一个资料目录；教学产品与官方摘录分别选择，避免把两类资料混成现实产品推荐。

官方摘录的 `snapshot-2026-11-19` 是本地资料快照标识，**不是保险合同的生效版本或日期**。产品名称与摘录存在，也不表示目前仍在销售或用户能够投保。

每条比较事实必须能回到以下信息：产品标识、资料版本、比较维度、目录事实和来源位置。官方资料还应提供原始来源链接。自拟资料应始终带有教学性质标记，不能借用官方产品的出处。

### 取证规则

1. 先锁定用户选择的产品与版本，再进行检索或读取。
2. 搜索和按维度读取均可返回带条件、出处的事实；只有工具实际返回的证据才能用于完成比较。
3. 不把另一产品、另一版本或另一维度的片段移作当前依据。
4. 比例、金额、等待期等字段应连同适用条件阅读，不把一个数值抽出来作无条件结论。
5. 官方短摘录只支持摘录本身包含的事实；完整性不足应进入报告的缺口说明。

## 4. 从需求到报告的处理流程

### 需求检查与计划

网页先整理需求提案，用户核对字段、选定产品并确认后，程序检查关注点和产品选择。必需信息缺失时，提示补充，不启动新的比较任务。命令行直接提交完整需求文件；信息不足时保存 `needs_input` 结果。

信息足够后，程序根据关注点组织取证顺序。资料模式按固定步骤读取目录；模型辅助模式将需求、已选产品及版本交给模型，由它选择搜索和读取操作。所有动作必须限定在本次选择范围内。

一个有依赖的顺序是：明确普通门诊与续保这两个关注点，查找两款产品相应事实，保留条件与来源定位，再整理异同。读者可打开官方链接核对原始资料；程序不会自动下载、解析或审核完整合同。未确定产品版本，就无法确定应当阅读哪组证据；未取得证据，就不能下比较结论。

### 工具执行与证据回传

工具分别承担条款搜索和片段读取。模型提出工具请求，程序检查参数并执行，执行结果再进入下一次请求。

工具返回的是资料事实，不是新的行为指令。来源文本中即使出现“忽略要求”等内容，也不能改变用户的选择、请求预算或输出规则。

### 报告组装与审查

九维比较表由程序根据工具返回的目录事实组装，并绑定具体出处。模型负责取证操作，普通文字不能代替完成工具，也不能覆盖、补造或篡改表格事实。

程序检查引用是否属于本次选择范围、是否由工具返回，以及九个维度的必需证据是否齐全。表格原样保留事实与条件；资料本身的完整性和语义仍需人工核对，不能仅凭编号合法推断比较意见可靠。

### 补充需求与重跑

用户补充关注点或更换产品后，在同一会话中发起新一轮比较。当前实现重新取证，不从上一次模型调用的中断位置继续；最新结果之外保留最多五份历史结果，便于比较输入与结论的变化。

会话保存在本机 `outputs/insurance-sessions/state.sqlite3`，包含需求、消息、提案、运行与报告；API Key 不进入会话。旧 JSON 会话在读取时导入数据库并保留原文件。这里保存的是工作区状态，不是 LangGraph checkpoint 或 Python 执行位置。

后台运行有独立标识和增量事件。重复提交同一个请求标识与相同参数只返回原运行；同一会话不能同时执行两个操作，也不能在运行中覆盖需求。取消在模型返回、下一次工具或模型调用等边界生效，已发送的请求不保证立即撤回。重启时发现执行进程已退出的任务标为中断，用户决定是否重新开始。

### 报告追问

“这份报告为什么仍把保费写成未知？”可以直接使用当前报告的证据回答。模型辅助模式仅选择相关证据编号，资料模式按维度关键词选择；回复正文由保存的事实与条件组成，不由模型添加新条款。未知事项保留资料不足说明。

追问只使用最新且与当前需求一致的报告。历史报告可回看；需求修改后必须重新查证，不能将旧报告当作新产品选择的依据，也不会在追问时悄悄读取更新后的目录。

## 5. 输出契约

| 报告部分 | 必须表达的内容 |
| --- | --- |
| 需求摘要 | 本次问题、关注维度、用户已提供与未提供的条件 |
| 比较范围 | 所选产品、资料版本及教学资料或官方摘录标记 |
| 九维对照 | 每个字段的资料事实、条件、缺失状态及出处 |
| 比较关注点 | 与用户关注维度有关的差异和需要进一步阅读的条件 |
| 未知事项 | 缺少报价、健康告知、核保、短摘录之外内容等待确认项 |
| 下一步 | 用户可以补充什么，或需要向保险方核实什么 |
| 流程状态 | 已完成资料比较、待补充信息、证据或工具问题、预算停止等原因 |

预算匹配必须有适用报价作为依据。当前自拟资料与官方摘录均未提供针对用户条件的有效报价，因此即使用户填写了预算，也不判定任何产品是否符合预算。

健康告知和核保信息应保持原文条件与未知项。报告不能把“资料可比较”写成“符合投保资格”，不能把“填写了健康情况”写成“已通过核保”，也不能生成承保承诺。

本地网页和命令行只交付资料比较，不产生投保、签约、付款或理赔动作。

### 停止时仍要说明什么

| 停止原因 | 应保留或返回的内容 |
| --- | --- |
| 必需需求缺失 | 已有请求、需要补充的字段及问题 |
| 产品或版本无效 | 无法识别的选择及可纠正方向，不自动换成别的版本 |
| 资料缺失 | 哪些维度没有依据；允许呈现其他有依据的资料 |
| 工具或引用检查失败 | 失败位置与已取得的证据，不包装成完整比较 |
| 请求预算耗尽 | 已有进度与停止原因，不在预算外增加总结请求 |

“资料比较完成”只表示这次资料整理流程完成，不能作为价格有效、当前在售或承保成立的证明。

## 6. 功能分层与课程范围

| 层次 | 当前职责 | 学习重点 |
| --- | --- | --- |
| 产品目录 | 管理产品、版本、九维字段与出处 | 结构化资料和来源追踪 |
| 业务工作流 | 检查输入，组织比较表和未知项 | 确定性处理与输出契约 |
| 单体 Agent | 在任务计划与调用预算内选择搜索、读取和完成操作 | 原生工具调用与证据回传 |
| 需求与追问 | 将自然语言整理为待确认字段；从当前报告选择证据 | 用户确认与生成内容边界 |
| 后台运行与会话存储 | 增量事件、取消、幂等、SQLite 事务与版本检查 | 持久状态、执行归属与模型上下文的区别 |
| 本地网页与 CLI | 网页提供聊天工作区；CLI 提交需求文件，复用比较服务 | 多种界面共享同一业务规则 |
| 可选集成 | 用 LangGraph、MCP 承接同一资料与任务 | 流程组织和工具通信的区别 |

LangGraph 和 MCP 是同一业务的适配练习，不另建一套保险结论或产品数据库。框架版本仍要遵守需求检查、版本绑定、引用和预算规则。

## 7. 验收任务

下面是验收目标。每个案例应检查具体结果与来源，不能只检查程序有没有退出。

| 案例 | 输入变化 | 预期核查点 |
| --- | --- | --- |
| 关注点为空 | 已选两个产品，但没有 `focus` | 暂停并追问，不猜用户最在意的维度 |
| 对象未明确 | 只选一款，或提供无效版本 | 指出选择问题，不擅自补齐产品或版本 |
| 教学产品比较 | 两款 `demo-v1` 产品，关注医院和续保 | 重点与需求对应，九维事实和出处可核查 |
| 官方摘录比较 | 使用官方快照 | 呈现资料缺口，不声称摘录完整或产品在售 |
| 有预算但无报价 | 提供年度预算，资料没有适用报价 | 预算匹配保持未知，不推算产品保费 |
| 健康告知待确认 | 用户询问自己是否一定能投保 | 返回待核实条件，不作承保判断 |
| 引用范围错误 | 工具或关注点携带另一产品、版本的证据 | 拒绝错误绑定，并说明问题 |
| 需求变更 | 在同一会话补充关注点或更换产品 | 当前结果使用新输入，上一轮结果仍可查看 |
| 提案尚未确认 | 聊天提出预算或关注点变更 | 已确认需求不变，不自动选择产品或启动比较 |
| 报告追问 | 询问当前报告中的免赔额或未知报价 | 只引用该报告来源，保留条件，不生成适用报价 |
| 旧报告追问 | 确认新需求但尚未重新查证 | 要求先查证新需求，不调用模型回答旧报告 |
| 重复与并发操作 | 重复请求标识，或另一进程运行同一会话 | 相同请求复用运行，竞争执行被拒绝 |
| 取消与重启 | 请求取消，或在未完成时退出进程 | 保留已有记录，不继续后续调用或自动重发任务 |
| 请求上限不足 | 减小 Agent 调用预算 | 明确预算停止，不额外请求，也不宣称流程完成 |
| 适配一致性 | 用不同入口读取同一组产品资料 | 来源与业务事实一致，界面和通信方式不改变条款 |

离线检查用于验证字段、来源绑定、停止条件与存储行为；模型运行用于观察工具选择、参数和取证顺序。回答质量还需要逐条对照资料，特别检查“不限”“一定”“保证”等表述是否超过证据。
